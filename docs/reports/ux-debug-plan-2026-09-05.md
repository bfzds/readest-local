## 1. 什么算"影响用户体验的 bug"（本计划的判定标准）

按伤害排序，满足其一即入列：

1. **卡死/挂起**：overlay 常驻、按钮无响应、界面锁死。
2. **交互失灵**：点了没反应、拖放落不进、快捷键/焦点丢失。
3. **数据损失感**：操作看似成功实际没保存；或保存了但界面显示旧状态。
4. **明显性能劣化**：启动慢、翻页卡、输入延迟（以体感为准）。
5. **视觉错乱**：控件重叠、残影、高亮不消失、错位。

不做：纯代码卫生、理论性竞态（无用户可见症状）、架构级改造（iframe origin 隔离、私有临时目录——已明确另立任务）。

## 2. 方法论（我的思路）

1. **旅程优先**：沿核心用户路径走查——`打开书库 → 导入/打开书 → 阅读翻页 → 进度跳转 → 划线标注 → TTS → 设置 → 关窗`。路径上的 bug 优先级天然最高。
2. **高 churn 审计**：git 近 30 笔提交改过的 UI/状态机代码，逐文件读，专找状态机洞（stale 轮次、finally 缺失、cleanup 不幂等）。
3. **状态机五问**（对每个 overlay/拖拽/异步流程问）：
   - 谁置位？谁复位？异常路径谁负责？
   - 并发两轮交错时，新轮会被旧轮污染吗？
   - 组件卸载/窗口失焦时状态会残留吗？
   - 失败时用户能看到什么（toast/静默/假成功）？
   - 复位动作本身会失败/被跳过吗？
4. **实机复现优先于脑内推理**：疑点先在 `pnpm dev`（WebView2）里复现，能复现才算 bug；复现不了但代码证明可达的，标注"代码级证明"。
5. **修复顺序**：先复现 → 最小修复 → 补回归测试 → test-runner 全量验证。

## 3. 重点区域与具体疑点（按风险排序）

### A. 书架拖拽引擎（风险最高：重写时间短、历史上坏过）

| # | 疑点 | 用户症状假设 | 验证方式 |
| --- | --- | --- | --- |
| A1 | 拖拽中源格子滚出 Virtuoso 视口被卸载 → ghost/淡化/命中引用悬空 | 拖到列表边缘自动滚动时拖拽失效或残影 | 实机：按住书滚轮滚动后松手 |
| A2 | `pointercancel`/丢失指针捕获路径不完整 | 来一条系统通知/切窗口后卡在"拖拽中"视觉态 | 代码走查 + 实机切窗口 |
| A3 | Escape 不能取消拖拽 | 用户无法反悔，只能丢到错误位置 | 实机 |

| A5 | 丢到空处/自身/所在组：是否有反馈 | 无响应无声，用户以为坏了 | 实机 |
| A6 | 拖拽落点保存失败（磁盘/锁超时）时 UI 与磁盘分叉 | 假成功 | mock 保存失败走查 |
| A7 | `groupBy !== 'group'` 时拖拽 gate 是否给提示 | 功能"消失"无解释 | 实机切排序模式后拖 |

| 阶段 | 内容 | 产出 |

## 5. 风险与边界

- 不重构、不顺手清理；每修一个 bug 独立可回滚。
- 拖拽引擎若发现设计级缺陷（如 pointer 路线根本不满足自动滚动），先报告方案再动手，不擅自推倒重写。
- 所有"卡死类"修复必须附带"如何再犯"的复现步骤，防止回归。
- test-runner 不可用（并发限额）时：如实报告并暂停验证步骤，不代替执行、不谎报通过。
